# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

iOS app (SwiftUI, iOS 17+) named **Mecateando** — the Xcode project/target/module name, scheme, and test target all match (`Mecateando`, `MecateandoTests`), as of the 2026-09-11 rename from the original scaffold name `GastosSMS`. The bundle id, `com.ridel007.gastossms`, was deliberately **not** changed in that rename (changing it would make iOS treat it as a different app entirely, forcing every test device to reinstall from scratch) — don't "fix" that mismatch. Tracks monthly expenses, either entered manually, pasted from bank/wallet SMS text, or shared in from Messages.app via a **Share Extension** target (Colombian banks — see "SMS capture roadmap" below). Two Xcode targets now: `Mecateando` (the app) and `ShareExtension`, sharing an App Group container.

## Project generation (XcodeGen)

The Xcode project (`Mecateando.xcodeproj`) is **generated, not committed** — `project.yml` is the source of truth. After cloning, or any time `project.yml` or the file layout under `Sources/`/`Tests/` changes, regenerate it:

```sh
xcodegen generate
```

XcodeGen is installed via Homebrew (`brew install xcodegen`).

## Build & test

Building/testing from the CLI requires `xcode-select` to point at full Xcode, not just the Command Line Tools:

```sh
xcode-select -p   # should print .../Xcode.app/Contents/Developer
sudo xcode-select -s /Applications/Xcode.app/Contents/Developer  # if not
```

Then:

```sh
xcodebuild -project Mecateando.xcodeproj -scheme Mecateando -destination 'platform=iOS Simulator,name=iPhone 15' build
xcodebuild -project Mecateando.xcodeproj -scheme Mecateando -destination 'platform=iOS Simulator,name=iPhone 15' test
```

Or open `Mecateando.xcodeproj` in Xcode and build/run/test from there (⌘R / ⌘U).

## Architecture

- `Sources/Mecateando/App/MecateandoApp.swift` — SwiftUI `@main` app entry point; owns the SwiftData `.modelContainer(for: Transaction.self)`.
- `Sources/Mecateando/Models/Transaction.swift` — SwiftData `@Model` for a single expense/income movement. `Transaction` does not declare `: Identifiable` explicitly — `PersistentModel` already conforms, satisfied by the `id: UUID` property. `category: Category` defaults to `.otros` directly on the property declaration (not just in `init`) — required so SwiftData's lightweight migration can backfill the field on rows saved before it existed, same reasoning applies to `CorrectionExample.category`.
- `Sources/Mecateando/Models/TransactionEnums.swift` — `MovementType`, `Currency`, `CaptureSource`, `Category` (all `String`-backed, `Codable`, `CaseIterable`). `Category` is the "what was this spent on" dimension (Vivienda, Alimentación, Transporte, ... `otros` as the mandatory fallback) — see the categories-and-charts analysis. `MovementType` and `Category` both have `init?(displayName:)` for mapping a generative model's free-text output back to the enum. `Category.color` gives each of the 10 real categories one fixed color from a palette the user supplied (mapped 1:1 in the order both were given); `otros` gets a neutral gray since the palette only has 10 colors for 11 cases. Imports SwiftUI (unlike the other model-adjacent files) for `Color` — same pattern already established by `systemImage: String` blurring the model/UI line on these enums.
- `Sources/Mecateando/Support/Color+Hex.swift` — `Color(hex:)`, a 6-digit-hex initializer (`"00C2CB"` or `"#00C2CB"`), backing `Category.color`.
- `Sources/Mecateando/Parsing/SMSParsingEngine.swift` — regex/keyword-based rule engine that extracts bank, movement type, amount, currency, merchant, payment method, and category from raw Colombian bank SMS text. Patterns are still mostly generic heuristics, not verified per-bank templates — see the doc comment at the top of the file before trusting exact wording (it also documents two real-message bug fixes: the amount regexes/`normalizeAmount` now accept *either* the Colombian "." -thousands/","-decimal convention or the English one, since a real Bancolombia transfer SMS used "$1,000,000"; and "transferiste" is in the `.transferenciaEnviada` keyword list). Bank/type/currency/category detection uses `String.range(of:options:[.caseInsensitive, .diacriticInsensitive])`; only amount/merchant/card extraction use `NSRegularExpression` (which has no diacritic-insensitive option, unlike `String.CompareOptions`). `extractAmount` has 3 fallback patterns in order: `$`/`COP`-prefixed, `pesos`/`COP`-suffixed, then `amountBareRegex` (a bare formatted number with no currency marker at all) — added after a real Banco Caja Social message ("Su pago por 2.119.221,76 para...") turned out to have neither a symbol nor "pesos"/"COP". `detectCategory` is a best-effort keyword match against the merchant name first, then the full text — never verified against real data, and `.otros` is always a valid non-failing result (category never affects `confidence`/`missingFields`/`needsReview`, unlike bank/amount/merchant).
- `Sources/Mecateando/Parsing/ParsedTransaction.swift` — output struct of the parsing engine, with a computed `needsReview` (low confidence or missing amount).
- `Sources/Mecateando/Parsing/GenerativeTransactionCandidate.swift` / `GenerativeExtractionService.swift` — the "Capa 2" generative fallback: Apple's on-device Foundation Models framework (`@Generable`/`@Guide`, `LanguageModelSession`), used only when `SMSParsingEngine` leaves `needsReview == true`. **Requires iOS 26.0** (far above this project's iOS 17+ deployment target) — every entry point is `@available(iOS 26.0, *)` and every call site is guarded with `if #available`, so the app must keep working identically on older iOS/devices without Apple Intelligence. `GenerativeExtractionService.refine` never throws to its caller — on any failure or unavailability it returns the input `ParsedTransaction` unchanged. The rule engine's own findings always win in the merge; the generative pass only fills fields the rules left empty. `refine` also accepts `[CorrectionExampleSnapshot]` — past user-confirmed transactions from the same bank — injected into the prompt as few-shot guidance; this is the only "learning" mechanism in place today (there is no public API to retrain the on-device model itself, see the GastosSMS generative-AI analysis).
- `Sources/Mecateando/Models/CorrectionExample.swift` — SwiftData `@Model` storing a confirmed SMS-derived transaction (raw text + final values) keyed by bank, written by `TransactionEditorView.recordCorrectionExampleIfNeeded` on every save that has both a bank and raw text, and read by `PasteSMSView.recentExamples(forBank:)` (most recent 3) to build the few-shot prompt above. Registered in the app's `modelContainer` alongside `Transaction`.
- `Sources/Mecateando/Support/CurrencyFormatting.swift` — `es_CO`-locale currency formatting (0 decimals for COP, 2 for USD).
- `Sources/Mecateando/Support/YearMonth.swift` — a plain year+month value type (not `Date`) used to represent "the month being viewed", with `.current`/`.previous`/`.next`, `init(date:calendar:)` (a transaction's date → its month), and a `dateInterval(calendar:)` for filtering `Transaction.date`. Exists because comparing bare `Date`s via `Calendar.isDate(_:equalTo:toGranularity:)` doesn't generalize to "the user is browsing a past month" — see the GastosSMS monthly-navigation-and-achievements analysis. Declares `init(year:month:)` explicitly alongside `init(date:)` — adding any custom initializer suppresses Swift's synthesized memberwise one.
- `Sources/Mecateando/Support/SpendingTrend.swift` — compares `selectedMonth`'s total against `selectedMonth.previous`'s (0 if that month has no transactions). `difference = previousTotal - currentTotal`; positive is `.better` (spent less — green up arrow), negative is `.worse` (spent more — red down arrow), zero is `.same`. This is also the "ahorro" figure the achievements system consumes.
- `Sources/Mecateando/Support/MonthlyTotals.swift` — `expenseTotal(for:in:)` and `categoryTotals(for:in:)`, the shared "sum a month's expenses" math used by `ContentView`, `AchievementsEngine`, and the charts, factored out once it was about to be written a third time. Returns `MonthlyTotal`/`CategoryTotal` — small named structs, not tuples, specifically so call sites can use `id: \.month`/`id: \.category` in `Chart`/`ForEach`; Swift keypaths don't reach into labeled tuple elements (only positional ones like `\.0`).
- `Sources/Mecateando/Views/RootTabView.swift` — app root (set as the `WindowGroup` content in `MecateandoApp`): a `TabView` with "Resumen" (`ContentView`), "Métricas" (`MetricsView`), and "Logros" (`AchievementsView`). Each tab owns its own `NavigationStack` — there's no shared/outer one. `.fullScreenCover`s `OnboardingView` on first launch, gated by `@AppStorage("hasSeenTutorial")` — an app preference (`UserDefaults`), deliberately not SwiftData, since it isn't user data.
- `Sources/Mecateando/Views/OnboardingView.swift` — 4-page paged walkthrough (`TabView` + `.page` style): capturing expenses, month navigation, the trend indicator, and achievements. "Saltar" or reaching the last page's "Empezar" both call `onFinish`, which `RootTabView` uses to flip `hasSeenTutorial` — this view has no idea persistence is involved.
- `Sources/Mecateando/Views/MonthNavigationBar.swift` — the ← [mes] → row, shared between `ContentView` and `MetricsView` (each keeps its own `@State selectedMonth`, independent of the other tab's) so the "no future months" rule only exists in one place.
- `Sources/Mecateando/Views/MetricsView.swift` — `monthlyComparisonChart` (`BarMark`, `selectedMonth` and the 5 before it, selected one highlighted) and, only when that month has any category spend, `categoryChart` (`SectorMark` donut, each slice colored with `entry.category.color` directly rather than Charts' auto-assigned `foregroundStyle(by:)` palette) + `categoryBreakdownList` (icon/name/amount per category, in matching colors — doubles as the donut's legend, since a manually-colored chart doesn't get an automatic one). Swift Charts is native since iOS 16, no `@available` gating needed, unlike Foundation Models. Originally lived in `ContentView`; moved to its own tab on request.
- `Sources/Mecateando/Achievements/AchievementTier.swift` — `AchievementTier` (id, minimum savings, points, title, SF Symbol) + `AchievementCatalog.tiers`, an ordered list of thresholds (example starting values, freely adjustable — nothing else depends on the exact numbers). `AchievementCatalog.tier(for:)` returns the highest tier a savings amount clears; tiers don't stack.
- `Sources/Mecateando/Achievements/AchievementsEngine.swift` — computes points/badges/history **entirely on the fly** from `Transaction` data every time (never drifts out of sync). `evaluate(transactions:)` walks every calendar month from the earliest transaction through the current month inclusive (including empty months — a quiet month after a big-spend one still counts as a save), comparing each to `SpendingTrend` against the month before it. `newlyUnlocked(_:seen:)` diffs that against `SeenAchievement` records to find tiers reached since the last visit — the one thing a purely-computed result can't answer on its own.
- `Sources/Mecateando/Models/SeenAchievement.swift` — SwiftData `@Model`, one row per (year, month, tierID) already celebrated. Exists only to gate the celebration sheet once per tier-per-month; badges/points themselves never read from it. Registered in the app's `modelContainer` alongside `Transaction`/`CorrectionExample`.
- `Sources/Mecateando/Views/AchievementsView.swift` — points total, badge list (locked/unlocked per `AchievementCatalog.tiers`), and full monthly history, all derived from `AchievementsEngine.evaluate`. `.onAppear` calls `checkForNewAchievements`, which inserts a `SeenAchievement` for every newly-reached tier (so it can only fire once) and presents `AchievementCelebrationView` as a sheet when there's something new. Shows `ContentUnavailableView` (not fake data) when there are no transactions at all yet.
- `Sources/Mecateando/Views/ContentView.swift` — main dashboard, scoped to `@State private var selectedMonth: YearMonth` (defaults to `.current`): total, transaction list, and swipe-to-delete are all filtered to that month via `selectedMonthTransactions`. `MonthNavigationBar` moves `selectedMonth`. `trendIndicator` shows `SpendingTrend` right under the total. Also has the "+" menu (manual entry / paste SMS), tap-to-edit. Charts live in `MetricsView` (separate tab), not here.
- `Sources/Mecateando/Views/TransactionEditorView.swift` — shared form for create/edit, driven by `TransactionDraft` (built from scratch, from a `ParsedTransaction`, or from an existing `Transaction`). Amount parsing tries the device's current locale first (so a `,` decimal from `.decimalPad` in Spanish locales works), falling back to `en_US_POSIX`. Takes an optional `onSaved: (() -> Void)?`, called right before this view dismisses itself on a successful save — lets a presenter that opened this as a nested sheet (only `PasteSMSView` today) dismiss itself too.
- `Sources/Mecateando/Views/PasteSMSView.swift` — paste/type raw SMS text; runs it through `SMSParsingEngine`, then (async, iOS 26+ only, if still `needsReview`) through `GenerativeExtractionService`, then hands the result to `TransactionEditorView` (presented as a sheet) for confirmation before saving. Always sets `TransactionDraft.aiNote` explaining what happened — whether the model ran, why it didn't (unsupported iOS, or `SystemLanguageModel.default.availability != .available`, which is the common case in the iOS Simulator — Foundation Models generally needs a physical device), and, when it did run, `GenerativeRefinementResult.summary` / `GenerativeTransactionCandidate.fieldSummary` — every field the model returned verbatim, before any merging or `Decimal` parsing — shown in the confirmation form so a miss is diagnosable (model didn't find the field vs. found it but `merged(into:rawText:)` failed to parse it) instead of a silent black box. Has an explicit "Cancelar" toolbar button, and passes `onSaved: { dismiss() }` to `TransactionEditorView` so this screen also closes once the nested sheet saves successfully — without that, `PasteSMSView` stayed open underneath after `TransactionEditorView` dismissed itself, with only an undiscoverable swipe-down to close it.
- `Sources/Mecateando/Views/TransactionRowView.swift` — list row. The secondary line (bank · category · date) shows category as its SF Symbol icon (with an `.accessibilityLabel`, since it has no visible text) rather than the full name, and a compact `d MMM yyyy` date (e.g. "10 Sep 2026") instead of the system's default date style — both to fit on one line without crowding.
- `Sources/Mecateando/Resources/Assets.xcassets` — app icon, accent color, and other asset catalog entries.
- `Sources/Mecateando/Preview Content/` — assets available only to SwiftUI previews (`DEVELOPMENT_ASSET_PATHS`), not shipped in the app.
- `Tests/MecateandoTests/SMSParsingEngineTests.swift` — unit tests for the parsing engine (amount normalization, bank/type detection, missing-field handling).
- `Tests/MecateandoTests/SmokeTests.swift` — trivial placeholder test from the original scaffold, class renamed `SmokeTests` (not `MecateandoTests`) to avoid a class sharing its exact name with the module/target it lives in.
- `Tests/MecateandoTests/` — unit test target (`MecateandoTests`), depends on the `Mecateando` app target via `@testable import`.

## SMS capture roadmap

iOS has no public API to read a device's existing SMS history, and there's no way to fetch new messages on app launch either — manual entry and paste-to-parse ("Fase 0") were the first capture path, and the **Share Extension** (below) is the second: the user selects a message in Messages.app, taps Share, picks Mecateando.

**The `IdentityLookup` Message Filter Extension was investigated and ruled out** — worth recording so it isn't re-attempted. Apple's own "SMS and MMS Message Filtering" documentation states the extension "can't access the network directly" and, critically, "can't write data to containers shared with the containing app." `ILMessageFilterExtensionContext` confirms this: its only method is `deferQueryRequestToNetwork(completion:)`, which defers to the *extension's own* server, never to the containing app. There is no documented mechanism for a Message Filter extension to hand message content, or even a plain notification, to the app it belongs to — its only output is a classification decision returned to Messages itself. This isn't a workaround-able implementation detail; it means the extension type is structurally unusable for capturing data into a third-party app, regardless of entitlements. (An earlier version of this document assumed otherwise, before this was checked against the actual docs — don't trust that assumption if it resurfaces elsewhere, e.g. in old memory/chat history.)

### Share Extension capture (implemented)

- `Sources/Shared/RawMessage.swift` — the only thing that lives in the shared App Group container (`group.com.ridel007.gastossms`): id, raw text, received-at. Compiled into **both** the `Mecateando` and `ShareExtension` targets (`Sources/Shared` is in both targets' `sources:` in `project.yml`) — a SwiftData model has to be linked into whichever module uses it, there's no framework boundary here.
- `Sources/Shared/SharedInboxContainer.swift` — `SharedInboxContainer.shared`, a standalone `ModelContainer` for just `RawMessage`, configured with `ModelConfiguration(groupContainer: .identifier("group.com.ridel007.gastossms"))`. Accessed directly (`SharedInboxContainer.shared.mainContext`), not through SwiftUI's `@Environment(\.modelContext)` — that environment only carries one container, and the Share Extension has no SwiftUI environment to inject into anyway.
- `Sources/ShareExtension/ShareViewController.swift` — the extension's `NSExtensionPrincipalClass` (set in `project.yml`'s generated Info.plist). A plain `UIViewController` (Share Extensions don't get a SwiftUI `App` entry point) that pulls plain text out of `extensionContext.inputItems` via `NSItemProvider.loadObject(ofClass: String.self)`, then hosts `ShareExtensionView` (SwiftUI) via `UIHostingController`.
- `Sources/ShareExtension/ShareExtensionView.swift` — the extension's only screen: show what was shared, a "Guardar" button that inserts a `RawMessage` into `SharedInboxContainer` and calls `context.save()`, then `onFinish()` → `extensionContext.completeRequest`. No parsing happens in the extension — it only captures text as fast/reliably as possible; `SMSParsingEngine` and the generative Capa 2 aren't even compiled into this target.
- `Sources/Mecateando/Parsing/SMSCaptureCoordinator.swift` — the rules→generative-fallback pipeline, factored out of `PasteSMSView` so it's not duplicated by the pending-shared-message flow below. `PasteSMSView.analyze()` is now a one-line call into this.
- `Sources/Mecateando/Views/ContentView.swift` — on `.task` (first appearance) and whenever `scenePhase` becomes `.active`, `checkPendingSharedMessages()` looks in `SharedInboxContainer` for a `RawMessage` not already being shown or skipped this session, runs it through `SMSCaptureCoordinator`, and presents the result via the same `TransactionEditorView` sheet used everywhere else. Saving removes the `RawMessage` (`markPendingMessageHandled`, wired as `onSaved`); cancelling leaves it in the inbox but adds it to an in-memory `skippedMessageIDs` set so dismissing doesn't just immediately re-show the same message — it resurfaces next app launch instead of being lost.
- `project.yml` — `Mecateando` target has an `entitlements:` block (App Group) and a `dependencies: [{target: ShareExtension, embed: true}]` (XcodeGen defaults `embed` to `false` for non-application targets, so this has to be explicit). `ShareExtension` is a `type: app-extension` target with its own matching entitlements and a generated Info.plist (`NSExtensionPointIdentifier: com.apple.share-services`, `NSExtensionAttributes.NSExtensionActivationRule.NSExtensionActivationSupportsText: true`).

Not done: no badge/indicator anywhere showing there's a pending shared message before the confirmation sheet appears; no `BGTaskScheduler` background processing (pending messages are only checked while the app is foregrounded/active, per above).
